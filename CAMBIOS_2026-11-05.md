# Corrección del recuento y control de reintentos · 5 noviembre 2026

## Evidencia y alcance

Los registros reales de Apps Script muestran 16 recuentos fallidos a las 12:43 y 18 a las 17:33 y 17:38. Los mismos trabajos volvían a cargar asistentes y movimientos cada cinco minutos. A las 17:43 aparece HTTP 429 por cuota. Los registros antiguos ocultaban el código del error de guardado: no permiten atribuir una cifra exacta de las 50.000 lecturas a este proceso.

El código enviaba `verify` dentro de escrituras REST. Este campo interno no aparece en el esquema público Write de la API REST v1 (https://firestore.googleapis.com/$discovery/rest?version=v1). El emulador no reproduce su rechazo; la causa concreta de cada error histórico no se puede recuperar de esos registros.

## Cambios

- Sustituir las comprobaciones `verify` del recuento por una transacción REST de lectura/escritura. Leer evento, revisión de asistencia, tarea y cursor de avisos dentro de la transacción; guardar resumen, avisos y eliminación de la tarea de forma atómica.
- Los movimientos y asistentes se leen solo para tareas pendientes. Si cambia su revisión durante el cálculo, se conserva la tarea y se revierte la transacción.
- Reintentos por versión de la tarea con esperas de 5, 15, 45 y hasta 60 minutos. Una versión nueva permite volver a intentarlo. Estado de reintento en Script Properties, sin lecturas extra de Firestore.
- Ante HTTP 400/401/403, detener el lote y pausar este trabajador 30 minutos; HTTP 429, 60 minutos. Evitar ejecuciones simultáneas mediante Script Lock.
- Registrar HTTP/status/intento, sin mensajes privados del servidor ni credenciales. Conservar tareas fallidas para volver a intentarlas.
- Mantener contadores, altas/bajas, aforo y avisos de plazas. No modificar interfaz, permisos ni plan de pago.

## Validación

Pruebas unitarias del trabajador: totales, transacción, rollback, cambio de versión, espera progresiva, circuito de fallos comunes y bloqueo de ejecuciones simultáneas. Prueba HTTP contra Firestore Emulator con las reglas del proyecto: resumen vacío, ascenso de espera con aviso en cola, escritura atómica, conflictos y permisos. Sin enviar mensajes reales ni consultar datos de producción.

La reducción real se comprobará cuando vuelva la cuota. No se garantiza que este sea el único origen del consumo. Las otras tareas y las cargas de la agenda requieren seguimiento separado.
